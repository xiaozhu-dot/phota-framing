## 一致性检查器在历史记录上的表现

我把检查器跑在所有 v16–v21 新手记录上，结果与人工报告逐条对照：

- **v21 海边（4:3 和 16:9）**：模型说"视线朝左但贴边"，而脸中心 x=.50。检查器报**矛盾**，与 2026-10-24 报告的人工结论一致。
- **v16 海边 4:3**：理由写"稍向右转取景"，最终动作却是向左。检查器报**方向疑点**，与同一报告一致。
- **v16 眺望（wife）**："视线朝画面左侧但贴近边缘"，脸中心 x=.28。没有主体框，检查器只报**待核验**，不定为错误。
- **v16 花丛（换个拍法）**："花枝集中在画面右侧"说的是花，不是人。第一版检查器把它误报成"人物偏右"，现在已修正：句子里只提景物、没提人物时跳过，并加了测试。

检查器只是报警器。它不知道坐标本身准不准：模型说"贴边"且坐标也写错时，它查不出来。所以 H2 / H3 必须人工对图确认后才能算硬错误。

## 待用户确认：冻结 v16 基线

运行清单见 `eval/stage0/baseline-v16-manifest.json`：

- **规模**：9 位作者 × 3 种输入（原图、4:3、16:9）× 2 种请求（首次、换个拍法），共 54 条逻辑请求，预计约 110–130 次 HTTP 调用，估算 ¥0.8–1.0。
- **停止条件**：
  - 每次 HTTP 调用最长 90 秒，不额外重试；
  - 累计估算费用超过 ¥1.5 立即停止；
  - 任一哈希变化就拒绝运行；
  - 不挑最好的一次，不为了好看重跑失败项。
- **运行步骤**：先执行 `node eval/stage0/run_baseline.mjs --freeze`，再执行 `--run`。

照片是新手在 Reddit 公开发的帖子，以前的评测已经发给 DeepSeek 做过推理。这次属于同一研究用途，不涉及私人照片。

## 运行之后需要人工完成

在 `eval/results/stage0-label-<名字>.html` 标注：

1. 先只看原片，标"保留即可 / 有值得解决的问题 / 无法判断"。
2. 再逐条看建议，标 H1–H6、这一步是否需要、建议适配四维分、现场关联。

有了这些标注，才能算硬错误率、不必要调整率、漏调率等指标。现在只有一位评分者，报告里会注明"单评"。
